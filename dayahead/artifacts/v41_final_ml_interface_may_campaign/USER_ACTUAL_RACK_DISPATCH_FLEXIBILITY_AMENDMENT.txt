# 1. CORE PRINCIPLE

Machine learning is used ONLY in Day-Ahead planning.

Actual does NOT:

- rerun runtime ML
- rerun future-workload ML
- recompute Q90
- re-optimize A0/M1/A1/MF
- change policy
- change selected IDC/site
- change admission/selected jobs
- create new migration
- alter MESS route


Actual performs ONLY:

REALIZED RUNTIME
+
RACK/GPU-LEVEL EXECUTION DISPATCH
within the already frozen Day-Ahead site decision.



# 2. PLANNED START IS A RELEASE TIME

Do NOT require:

ACTUAL_START_j == DA_PLANNED_START_j


Instead freeze:

ACTUAL_START_j >= DA_PLANNED_START_j


Interpret:

DA_PLANNED_START_j
=
earliest authorized execution time


Actual execution may be delayed if rack/GPU capacity is not yet
physically available because earlier jobs run longer than predicted.



# 3. SAME IDC / SITE MUST REMAIN FROZEN

For every job:

ACTUAL_SITE_j = DA_SITE_j


No cross-site repair.

No site reassignment.

No workload migration created in Actual.


The only spatial flexibility allowed is:

RACK assignment
within the already frozen IDC/site.



# 4. ACTUAL RACK ASSIGNMENT

At Actual execution time, assign each job to a physically feasible
rack or set of authoritative rack resources within its frozen site.

Rack assignment may differ from the preliminary Day-Ahead rack
representation ONLY if the existing Actual contract already allows
rack-level execution assignment.

Do NOT create a new rack topology or capacity.

Use the authoritative existing rack/GPU capacities.



# 5. EARLIEST FEASIBLE EXECUTION

For every selected job j:

ACTUAL_START_j
=
earliest t >= DA_PLANNED_START_j

such that its frozen site can provide the required physical
rack/GPU capacity.


Then:

ACTUAL_END_j
=
ACTUAL_START_j
+
REALIZED_RUNTIME_j


No artificial shortening of runtime.

No GPU clipping.



# 6. RESOURCE CAPACITY REMAINS HARD

At every exact execution event:

GPU_OCCUPANCY[i,t]
<=
GPU_CAPACITY[i,t]


and all authoritative rack-level capacity constraints must hold.

RUNTIME_OVERRUN_INDUCED_RESOURCE_CONTENTION


Then resolve the physical execution through rack/GPU availability
delay, NOT by changing Day-Ahead policy.

# 8. THIS IS NOT ACTUAL RE-OPTIMIZATION

The following remain frozen from Day-Ahead:

- admitted/selected job set
- IDC/site
- policy
- migration
- WAN decisions
- MESS route
- A0/M1/A1/MF decisions


Actual rack dispatch does NOT optimize the grid objective.


It only constructs a physically executable realization of the frozen
Day-Ahead job plan under realized runtimes.



# 9. NO EARLY START

A job may NEVER be moved earlier than its Day-Ahead planned start.

Require:

ACTUAL_START_j >= DA_PLANNED_START_j


This prevents Actual information from creating an unrealistically
better schedule than the Day-Ahead plan.



# 10. DELAY PROPAGATION

If runtime overrun delays a job, the resulting occupancy may also
delay later jobs at the same site.


Allow deterministic delay propagation.


Do NOT drop later jobs merely because an earlier job overran,
unless the authoritative terminal/horizon contract makes their
execution impossible.


Do NOT invent a new cross-day completion rule.

Use the already-authoritative terminal/carryover semantics.



# 11. SIMULTANEOUS JOBS

If multiple jobs become eligible at the same time:

preserve the existing authoritative Day-Ahead ordering/tie-break rule.


Do NOT reorder jobs using Actual runtime knowledge.


If an existing deterministic rack-dispatch ordering already exists,
reuse it exactly.
