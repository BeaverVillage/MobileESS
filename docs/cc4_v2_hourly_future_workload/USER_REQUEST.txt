# 1. New scientific definition

CC4-v2에서 ML과 optimizer의 역할을 분리한다.

## ML의 역할

ML은 **headroom이나 reserve 자체를 예측하지 않는다.**

ML이 예측해야 하는 것은:

> D−1 18:00 시점에서 아직 submit되지 않았지만 다음날 새롭게 도착할 Job들이 만들어낼 future GPU-work arrival.

즉:

[
\hat W\_{D,h}^{q},
\qquad q\in{0.5,0.9}
]

where

[
h=0,\ldots,23
]

and each bin represents one local-clock hour of day D.

Prediction issue time:

[
D-1;18{:}00
]

Target day:

[
D;00{:}00 \sim D;24{:}00
]

Hence lead time differs by target hour and is approximately 6–29 h.

---

# 2. New target definition

For each target day D and hour h:

\sum\_{j:
submit_j\in[D,h,h+1)}
GPU_j \times runtime_j
]

Unit:

[
[\mathrm{GPU\cdot h}]
]

Important:

This is **arrival workload**, not workload that must be fully executed inside that same hour.

Example:

A future job submitted at 14:20 requests 4 GPUs and has a required runtime of 2.5 h.

It contributes:

[
4\times2.5=10;\mathrm{GPU\cdot h}
]

to the 14:00–15:00 arrival bin.

Its processing may occur after 15:00.

This distinction must be explicitly documented.

Use the same job eligibility / workload-accounting population as the frozen CC4 authority wherever scientifically applicable.

Do not silently broaden or shrink the workload population.

If a difference from the frozen CC4 job population is unavoidable, stop promotion and document:

- exact population difference;
- affected job count;
- affected GPU-h;
- scientific reason.

---

# 3. Remove forecast-side physical cap

The new forecast output must NOT be clipped by:

- 780 × H physical capacity;
- historical cap;
- scheduler headroom;
- any optimizer-derived capacity.

Do NOT use:

\min(\hat W,C\_{phys},C\_{hist})
]

for model evaluation.

The forecast layer must output its probabilistic estimate directly:

[
\boxed{
\hat W\_{D,h}^{50},
\hat W\_{D,h}^{90}
}
]

Physical feasibility remains a later optimizer responsibility.

This experiment does NOT modify the optimizer yet.

# 4. Strict causal information boundary

At issue time

[
D-1;18{:}00
]

only information causally available by that timestamp may be used.

Forbidden as model inputs:

- jobs submitted after issue time;
- future realized arrival counts;
- future runtime values unavailable at issue time;
- future queue state;
- future Actual values;
- future workload summaries constructed using target-day jobs;
- any feature whose timestamp maturity is later than the issue timestamp.

Future observations may only be used as supervised labels.

All features must carry an explicit maturity audit.

Reuse the causal feature logic from the existing CC4 offline experiment wherever possible.

Preserve existing 71-feature LightGBM lineage if valid, but adapt features appropriately for hourly target rows.

Add only causal features such as:

- target hour of day;
- lead time;
- weekday / calendar variables;
- historical arrival workload lags;
- historical workload profile statistics;
- historical burst indicators;
- existing causal system/context variables already authorized in CC4.

Do not introduce future leakage to improve coverage.

# 9. Calibration

Q90 means nominal 90% probabilistic coverage.

Use only causal calibration.

A valid approach is:

- chronological expanding calibration;
- mature labels only;

# 10. Metrics

The primary success criterion is NOT merely “coverage > 90%”.

A trivial huge prediction is not considered a successful model.

For each model report:

## Probabilistic forecast quality

### Q90 empirical coverage

[
Coverage=
\frac{
\#{W^{actual}\le\hat W^{90}}
}{
N
}
]

Nominal target:

[
90%
]

Interpretation:

- approximately 90% = calibrated;
- very low coverage = underprediction;
- extreme overcoverage such as 98–100% is overconservative and NOT automatically a success.

Report calibration error:

[
|Coverage-0.90|
]

### Q90 pinball loss

Primary sharpness/accuracy metric.

### Q50 pinball loss

### MAE / RMSE for Q50 or median prediction

### Mean prediction-to-realized requirement ratio

[
\frac{\sum \hat W^{90}}
{\sum W^{actual}}
]

### Excess reserve proxy

[
\sum_h
\max(\hat W_h^{90}-W_h^{actual},0)
]

normalized by total realized GPU-work.

# 12. Statistical comparison

Use day-level dependence.

Do not treat 24 hourly rows from a day as 24 independent statistical samples.

Use paired day-block bootstrap or an equivalent paired day-level uncertainty procedure.

For candidate vs LightGBM report:

- Δ Q90 pinball;
- Δ calibration error;
- Δ requirement ratio;
- 95% CI.

Do not declare a model superior if the improvement is within uncertainty.

# 13. Selection rule

Select a model only after all registered experiments are complete.

Priority:

1. no leakage / authority integrity PASS;
2. Q90 calibration close to 90%;
3. lower Q90 pinball;
4. reasonable prediction requirement / sharpness;
5. robustness across development, Dec–Feb, and May;
6. positive/burst behavior;
7. computational practicality.

Do not select purely because overall coverage exceeds 90%.

A candidate with 99% coverage and massive overprediction is not a valid success.

Target operating range for nominal Q90 should be approximately:

[
0.88\sim0.92
]

with lower pinball loss preferred.

A value slightly outside this range may still be scientifically acceptable but must be flagged and explained.
