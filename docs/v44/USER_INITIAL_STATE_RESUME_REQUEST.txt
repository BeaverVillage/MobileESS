## 2. May02~07 초기 RUNNING Job 문제 해결

현재 V44 Input Manifest에서 다음이 미해결 상태다.

| 날짜 | 초기 RUNNING | Site 미확정 |
|---|---:|---:|

| May03 | 297 | 116 |

| May05 | 355 | 40 |
| May06 | 360 | 30 |
| May07 | 403 | 19 |

총 213 UID의 초기 사이트가 미확정이다.

### 1차: 기존 Source에서 복원

각 날짜의 초기 RUNNING UID를 다음 자료와 정확히 대조하라.

- PR189의 날짜별 NATIVE_INPUT 및 Known Population
- PR148 B0의 초기 상태·실제 실행 기록
- R0 Reference Jobs
- Source Site 및 Current Site 필드
- 기존 초기화 Receipt
- V43 May01 초기화 코드와 검증 정책

UID, 날짜, Issue 시각, GPU Gang, 호환 사이트, Source Site를 기준으로 대조한다.

**Issue 시점에 이미 알려진 실행 사이트가 실제 Source에 존재하면 그것을 우선 사용한다.**

다른 날짜의 최적화 결과를 복사하거나 미래 Actual의 실행 결과를 Planning 초기 상태에 누설하지 마라.

### 2차: 연구용 초기 사이트 가정

원본 Source를 모두 확인해도 사이트가 제공되지 않는 UID는, 기존 V43 May01과 동일한 원칙의 **결정론적 연구용 초기화**로 처리하라.

기준:

1. 해당 날짜의 Issue 시각에 관측된 RUNNING UID만 사용
2. Source Site가 있으면 우선 사용
3. 기존 Reference Site가 유효하면 사용 가능
4. 남은 UID는 호환성·GPU/Rack Capacity를 만족하는 사이트에 결정론적으로 배정
5. 동일 Source/UID/Seed면 동일 초기 상태를 재현
6. 임의의 미래 Job 완료·Runtime 정보 사용 금지
7. 초기 RUNNING Job을 새 Pre-site 또는 Migration으로 분류하지 않음
8. 초기 GPU 총량 및 사이트별 자원 제약 검증

불가능한 UID를 강제로 배정하지 마라.

가정으로 정한 UID는 반드시 `INITIAL_RUNNING_SITE_MODEL_ASSUMED`로 표시하라.

Source로 확인된 초기 사이트와 연구 가정으로 복원한 초기 사이트를 별도 집계한다.

**초기 사이트에 대한 실제 관측 증거가 없는 것과, 독립적인 연구용 Case를 실행할 수 없는 것은 구분해야 한다.**

1. 기존 Native Producer에서 고정 초기 위치·SOC가 연구 설계인지 확인

6. 모든 Arm에서 동일한 날짜와 동일한 실험 가정 유지
7. 이전 날짜 최적해·미래 SOC 사용 금지

새로운 MESS 초기 상태 최적화 알고리즘을 만들지 마라.

이 작업의 목적은 존재하지 않는 날짜별 관측값을 발명하는 것이 아니라, **원래 연구 모델의 초기 상태 가정을 정확히 복원하고 명시하는 것**이다.

## 7. Resume 및 Stage Checkpoint 문제 해결

현재 V44에서 가장 중요한 나머지 문제는 **Binary Stage Checkpoint 복원 미인증**이다.

PR189의 기존 Worker/Coordinator/Restart 기능을 조사하고, V44의 Stage별 Resume에 필요한 기능만 재사용하라.

### 대상 Stage

B1:
- A1
- Actual/Fresh

B2:
- K48 M1
- M1 Joint
- Actual/Fresh

B3:
- A1 Reuse
- K48 M1
- M1
- A2
- K48 M2
- M2
- Actual/Fresh

### Resume 필수 조건

1. 정확한 Day/Arm/Stage/Attempt 복원
2. 기존 Source/Case/Hardware SHA 검사
3. 실제 PID 및 생성시각 확인
4. 기존 Worker가 생존 중이면 중복 실행 금지
5. OS Lock과 Native Inflight 확인
6. Native Used/Remaining 정확히 복원
7. K48 300초와 Joint 900초 원장 분리
8. 이전 Native 호출시간 초기화 금지
9. 동일 Case의 FULL 검증 가능해 보존
10. 유효한 Global LB와 단순 제한 모델 Bound 구분
11. 부모 Stage의 동결 AIDC/MESS 결과 무결성 확인
12. 복원 불가능한 Checkpoint는 명시적으로 차단

### 두 가지를 분리하라

**정상적인 Stage 완료 후 Resume**

완료된 Stage Result와 Source/Case/Checkpoint 영수증을 검증하여 다음 Stage에서 계속 진행할 수 있어야 한다.

**Stage 실행 중 비정상 종료**

기존 Budget과 Native 상태를 정확히 정산할 수 있을 때만 안전하게 복원한다.

Gurobi 내부 B&B 탐색 상태가 남아 있지 않다면 탐색 상태까지 복원됐다고 주장하지 마라.

유효한 이전 Incumbent만 남았다면 이를 정확히 검증하고, 기존 예산을 차감한 상태에서 재진입 가능한지 별도 계약으로 처리한다.

사용되지 않은 과거 결과나 다른 날짜의 해는 사용하지 않는다.

### Resume가 불가능한 경우

- 실패 Attempt 원장 보존
- 재시작 허용 여부 별도 표시
- 해당 Stage만 BLOCKED
- 다른 날짜/Arm 캠페인은 계속 진행
- 자동 Native Clock Reset 금지
- 기술 오류와 정상 TIME_LIMIT 구분

`RECONCILED_STAGE_CHECKPOINT_REQUIRED`라는 상태만 선언하고 구현을 끝내지 마라.

실제 Checkpoint 복원 경로를 구현하고, 소규모 테스트에서 정상 완료·Crash·중복 Worker·손상된 SHA·시간 소진 사례를 검증하라.

복원이 기술적으로 불가능한 범위는 정확히 `NOT_SUPPORTED`로 남긴다.

## 9. 입력 인증의 판정 기준 개선

기존 V44에서는 일부 관측 근거가 없다는 이유만으로 `INPUT_NOT_READY` 처리하고 있다.

이번에는 다음 세 상태를 명확히 구분하라.

**SOURCE_VERIFIED**

실제 날짜별 원본 Source 또는 기존 인증된 자료로 확인된 초기 상태.

**MODEL_ASSUMED_VERIFIED**

독립 일별 연구에서 명시한 초기 상태 가정으로, 정확한 UID·물리 용량·호환성·Source 범위를 만족하는 것이 검증된 상태.

**INPUT_NOT_READY**

원본 Source도 없고, 검증 가능한 연구 가정으로도 구성할 수 없거나 물리 제약을 위반하는 상태.

Source 관측값이 아니어도 연구 가정이 정확하고 재현 가능하다면, `MODEL_ASSUMED_VERIFIED`로 준비할 수 있도록 하라.

단, Source 인증을 확보한 것처럼 보고하지 마라.

May01의 기존 MODEL_ASSUMED 상태와 May02~07의 가정은 동일한 기준으로 관리한다.

실험 전체에 공통된 초기 상태 가정을 적용한다면 B0/B1/B2/B3의 비교 공정성도 확인하라.

## 10. SVR11과 병행 작업하는 방법

현재 SVR11 이식이 진행 중이므로 다음 순서로 수행하라.

**병행 단계**

- PR189 초기 입력 조사
- May02~07 RUNNING UID 복원
- MESS 독립 일별 초기 가정 복원
- 날짜별 Source Manifest 수정
- Stage Checkpoint 및 Resume 구현
- 입력/OS Lock/Resume 경량 테스트

이 작업들은 SVR11의 하드웨어 설치나 Forecast 계수 생성 파일을 건드리지 않는 범위에서 먼저 진행한다.

**통합 단계**

SVR11 코드가 동결되면:

- 새 SVR11 Equipment/Scenario SHA 적용
- Planning/Actual Driver 연결
- 날짜별 전기계수 생성 경로 검사
- Native0 및 짧은 OpenDSS 물리 검증
- 최종 회귀 테스트
- PRESTART Certification 갱신

기존 SVR 작업을 중단하거나 그 소스를 다른 Branch의 이전 버전으로 덮어쓰지 마라.

동시 파일 수정 충돌이 발생하면 별도 Commit으로 분리하고 정확한 최신 HEAD에 통합하라.

PR233에 최종 통합한다.
