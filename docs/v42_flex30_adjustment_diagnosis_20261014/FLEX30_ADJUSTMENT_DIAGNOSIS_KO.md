# FLEX30 조정 실행 병목 — 고유 Job 기준 진단

현재 자료에서는 참여율보다 **미래 예약의 실행 전환과 Q50 서비스·계통 평가 경계**를 먼저 개선해야 한다. 승인된 유연 행동을 선택하지 않는 비율은 작다. 기존 674개 참여 Job과 전체 62개 조정 Job을 같은 모집단으로 계산한 비율도 정정해야 한다.

## 1. 62개와 674개의 모집단

E1/FLEX30/GRID의 활성 양수 예산 참여자는 674개다. 실제 DELAY 6개·PREPLACE 56개는 모두 고유 Job이지만, 그중 참여자는 **39개(DELAY 6·PREPLACE 33)**다. 나머지 PREPLACE 23개는 기존 모델의 zero-delay placement 권한을 사용했다. 따라서 참여자의 조정률은 62/674가 아니라 **39/674 = 5.7864%**다.

참여자 PREPLACE 33개 중 9개도 기존 모델 placement 권한을 함께 가진 Known이며, 나머지 24개는 연구 계약 placement 권한을 사용하는 Unknown이다. DELAY 6개는 Known이다. 따라서 39개는 참여 집단에서 조정한 수이지, 연구 계약만의 순수 인과 효과 39개라는 뜻은 아니다. E0와 C는 제어 경로도 달라 별도 동일 경로 반사실 없이 marginal effect로 승격하지 않는다.

공간 조정은 참여자 33개, 시간 조정은 참여자 8개(DELAY 6·시간도 바뀐 PREPLACE 2)이며 시간 조정의 시작 시각 차이 합계는 8,100초다. 두 집합이 겹치므로 33+8을 고유 조정 수로 더하지 않는다. 기준은 최종 공개 causal R0이고, 일반 자원 대기나 과거 취소 명령에서 누적 차감한 지연 의무와 구분한다. 작업 수만으로 이동한 GPUh·전력 또는 AC 개선을 주장하지 않는다.

## 3. 205개 예약 실행 실패

205개 모두 미래에 선택·예약한 명령과 실행 시 재검사 실패 기록을 갖고 있다. 153개는 나중에 일반 START로 시작했고 52개는 Pending으로 남았다. 취소·재기준 후에도 기존 지연 의무를 환불하지 않았기 때문에, 최종 START 라벨이 추가 지연 의무 0을 뜻하지 않는다.

이미 공개된 시작·완료·GPU release 시각만으로 현재 GPU를 재구성했다. Full96 저장 점유 배열과 최대 수치 오차는 4.2633e-14 GPU였다. 적분을 나누는 순서가 달라 raw byte 동일성을 주장하지 않으며 비교 허용오차 1e-9 GPU는 감사 수치 비교에만 사용했다. 물리 정격이나 운영 허용오차를 바꾸지 않았다.

| 205개 집단의 재검사 실패 | 실패 발생 수 | 영향을 받은 UID 수 |
|---|---:|---:|
| 현재 whole-gang GPU 부족 | 428 | 171 |
| 미래 예약 또는 Q50 점유 프로파일 충돌 | 1,128 | 176 |
| 현재 Original affine 계통 Hard | 92 | 89 |

발생 수는 재시도를 포함하며 UID 집합도 서로 겹친다. 세 UID 수를 더해서 205개로 해석하지 않는다.

이 중 **174개 UID의 592개 실패 사건**에서는 당시 GPU와 선택 명령을 지금 시작할 경우의 Original affine 계통 검사는 가능했으나 미래 예약·Q50 프로파일 충돌로 거부됐다. 이는 현재 GPU 부족과 미래 예약 충돌을 구분해야 한다는 근거다. 작업 전체 미래 구간의 실행 가능성, 미래 충돌의 불필요성 또는 Fresh AC 안전성을 증명하는 것은 아니다. 원래 미래 자원 검사를 삭제해 이들을 통과시킬 근거로 사용하지 않는다.

현재 로그만으로 충돌 상대가 Running overrun인지, 아직 실행하지 않은 다른 예약인지, 정확히 어느 미래 구간이 부족한지 모두 복원할 수는 없다. 이 정보는 이후 운영 개선에 필요한 우선 기록 항목이다.

## 4. 317개의 Q50 Hard 경계

317개 모두 적어도 한 번 현재 자원·현재 가드를 통과해 유연 후보를 점수 평가했지만, 어떤 유연 후보도 Q50 Hard 승인을 받지 못했다. UID별 이력에는 A2 literal service + candidate delta의 용량 경계와 Original planning voltage 거부가 모두 있었다. 반복 reason 관측 수는 각각 27,039개와 107,535개이며 같은 후보에서 두 사유가 함께 발생할 수 있다.

기존 용량 사유는 음수 프로파일과 상한 초과를 하나로 기록한다. 둘은 별도 의미이므로 단순히 실제 GPU가 부족했다고 결론 내리지 않았다. 후보의 start 시각도 모든 점수 행에 저장돼 있지 않다.

이를 확인하기 위해 정렬한 첫 20개 UID의 첫 점수 평가 사건에서 가능한 기록된 start offset을 모두 시험했다. 저장 Q50 점수뿐 아니라 위반 사유 수와 슬롯 집합이 일치하는 해석만 사용했다. 598개 점수 행의 재계산 오차는 0이었다. 이 20개 UID는 모두 적어도 하나의 **literal Q50 상한 초과** 후보가 확인됐고, 명확한 음수 프로파일 후보가 확인된 UID는 0개였다. 일부 다른 후보는 용량 상한은 넘지 않지만 voltage 조건으로 탈락했다.

이 20개는 수학적 재현 witness이며 전체 317개의 방향별 비율 추정 표본이 아니다. 실제로 관측한 GPU 점유와 고정 A2 Q50 서비스·익명 작업 배분의 예상 점유도 구분한다. 현재 입력에서는 고정 Q50 서비스와 이동 후보가 경쟁하는 미래 슬롯 및 전압 제약이 유연 행동을 제한한다. 이를 해소하려면 어떤 원본 서비스 배분·계통 계약을 보존하는지 먼저 명시해야 하며, Q50 작업을 임의 삭제하거나 Q90과 함께 무조건 이월시키지 않는다.

## 5. Selector가 지나치게 소극적인가?

현재 증거에서 주된 병목은 선택 순위가 아니다. 유연 후보가 승인됐지만 끝까지 선택되지 않은 Job은 17개다. 그중 14개는 기준 행동의 Q50 점수가 더 좋았고 3개는 Q50 동점이었다. Q50가 선택 행동보다 1e-9를 넘어 더 좋은 승인 유연 후보를 무시한 사건은 0개였다. 참여자의 candidate limit 잘림도 0개였다.

Q50 동점 3개의 비선택 대안 Q90 구성요소는 전부 저장되지 않아, Q90 위험과 최종 부담 순위의 기여를 완전히 분해할 수 없다. 따라서 모든 선택이 최적이었다거나 소극성을 완전히 배제했다고 주장하지 않는다. 다만 점수 가중치·참여율·후보 상한을 먼저 늘리거나 조정을 강제할 근거는 확인되지 않았다.

## 6. 반영한 진단 개선과 운영 개선 우선순위

이번에 고유 UID별 참여·원래 placement 권한, 생성/승인/선택/실행, 선택 명령 재검사, 현재 GPU/미래 예약, 공간/시간 조정을 분리한 재현 가능한 진단을 추가했다. 674개의 상세 표와 전체 62개의 모집단 대조를 공개한다. 기존 Source, Case, Policy, Raw, Full96 결과는 수정하지 않았다.

운영 개선은 다음 순서로 진행하는 것이 근거에 맞다.

1. **미래 예약 실행 전환:** 충돌 resource/구간/상대 UID/상대 상태(RUNNING 또는 BOOKED), 당시 공개 elapsed 및 원래 Q50 booking을 기록한다. 실행 전에 관측 상태와 미래 예약을 재조정하는 방법을 같은 FLEX30에서 비교한다. R0와 B를 갱신·환불하거나 실제 Running을 퇴출하는 방법은 제외한다.
2. **Q50 Hard 거부:** negative reference support, nominal capacity upper exceed, voltage를 별도 이유와 방향·슬롯·수치로 남긴다. 현재 실제 자원 가능성과 literal A2 미래 서비스 평가를 혼동하지 않는다. 원본 Q50/CC4·서비스 보존·계통 정격을 유지한 방법만 검토한다.
3. **Overrun Migration 지원:** 공개된 Running 관측과 원본 Runtime provider를 보존하면서, nominal envelope가 없는 작업의 판단 근거를 별도 검토한다. 미래 Actual 잔여 서비스·완료시간을 사용하거나 중단 시간을 0으로 만들지 않는다.
4. **선택 순위:** 위 병목을 처리한 후에만 같은 Q50 성능에서 Q90 위험·예약 신뢰성·불필요한 부담을 비교한다. 비선택 대안 Q90 값까지 기록해 세 동점 사례를 설명한다.

이 진단만으로 운영 행동을 바꿔 물리적으로 가능하다고 승격하지 않았다. 연구 정책을 변경할 때는 새 Source/Case와 Native0 fixture, 동일 May01의 별도 조건부 canary 및 그 실행 영수증으로 검증한다. 개선은 실행 전환뿐 아니라 처리량·Queue·Carry-over·계통 점수·불변 지연 예산을 함께 비교한다. 과거 FULL·Gap·Fresh 결과를 새 정책에 이전하지 않는다.
