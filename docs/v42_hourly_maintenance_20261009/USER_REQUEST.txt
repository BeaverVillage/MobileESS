# Codex — V42 B1/B2 May31 캠페인 1시간 자동점검·원인 분석·코드 복구·자동 재개

## 0. 사용자 최종 지시

현재 진행 중인 B1/B2 5월 캠페인 구현과 실행을 계속하라.

기존 작업을 중단하거나 처음부터 다시 시작하지 마라.

추가로 **Codex 예약 자동화를 매 1시간마다 실행**하도록 설정한다.

자동화 이름:

`V42 May B1-B2 Hourly Recovery`

실행 간격:

`RRULE:FREQ=HOURLY;INTERVAL=1`

작업 프로젝트:

`D:\MobileESS_v42`

브랜치: `v42`

기존 PR: #189

기존 캠페인 Coordinator가 계속 실행을 담당한다.

Codex는 매시간 상태를 진단하고 필요한 경우 코드·알고리즘을 수정하여 검증된 개선을 적용하는 유지보수 담당자다.

**정상 실행 중인 Solver를 매시간 중단하거나 재시작하지 마라.**

Codex 자동화는 캠페인 프로세스를 대체하지 않는다.

## 1. 매시간 확인할 사항

매 실행 시 다음을 점검하라.

### 전체 실행 상태

- Coordinator 실행 여부
- Worker PID / 생성시각 / 명령줄 동일성
- Heartbeat 갱신 여부
- 현재 B1/B2 Phase와 날짜
- 완료된 날짜 수
- PASS / TIME_LIMIT / FAIL / PENDING
- 최근 1시간 동안 새로 발생한 실패
- 중복 Worker 실행 여부
- Checkpoint 및 Runtime Ledger 무결성
- Windows Task Scheduler / Monitor 상태
- Codex 작업과 캠페인 프로세스의 독립성

### 최적화 상태

- 현재 Native Runtime
- 실제 Wall Time
- Solver Status
- 정수해 존재 여부
- 검증된 UB
- 독립 인증된 Global LB
- Certified Global Gap
- 진행 중인 최적화 단계
- 최근 1시간 동안 목적값·Gap 변화
- 시간제한 도달 여부
- 모델 생성·Presolve·LP·MILP·인증 단계별 시간

단순히 CPU 사용률이 낮거나, Solver가 장시간 같은 Gap에 있다는 이유만으로 오류라고 판단하지 마라.

OS 프로세스·Solver 로그·실제 상태를 교차 검증하라.

## 2. 오류 발견 시 자동 원인 분석

다음 상황을 발견하면 원인을 조사하라.

- Python exception
- Adapter interface error
- Input/Time-axis mismatch
- File SHA mismatch
- Worker crash
- Coordinator crash
- Checkpoint corruption
- Gurobi numerical failure
- Native infeasible
- TIME_LIMIT
- Independent certificate failure
- Original physical replay failure
- Fresh OpenDSS AC failure
- Monitor/Watchdog failure

각 오류를 다음처럼 구분한다.

### A. Infrastructure 오류

예:
- 파일 경로 오류
- 프로세스 재시작 문제
- Logger/Checkpoint 오류
- Windows 권한 문제
- Worker와 Coordinator 사이 인터페이스 오류

기존 코드를 최대한 재사용해 수정하라.

회귀 테스트 통과 후 안전하게 실행환경을 복구한다.

### B. 최적화 알고리즘 병목

예:
- 원본 LP 생성 과다
- Presolve 또는 Matrix assembly 병목
- Exact LB 인증 시간 과다
- Gap 정체
- 유효한 정수해 탐색 실패
- 최적화 시간 초과

해당 원인을 수치·Solver 로그·프로파일링 증거로 확인하라.

필요하다면 **기존 최적화 알고리즘을 개선해도 된다.**

다만 기존 모델과 동치인 방법을 우선 사용한다.

허용되는 개선 예시:
- 기존 검증된 모델 압축 재사용
- 정확한 중복 행 제거
- 동치성이 증명된 변수·행 감소
- 기존 Pricing/LP/정수 최적화 코드의 실행 효율 개선
- Matrix/CSR 조립 및 캐시 효율 개선
- 기존 Exact Dual Certificate 계산 효율 개선
- Solver 설정에 대한 근거 있는 검증
- 원본 문제 전체에 유효한 Exact Cut 또는 Valid Inequality

개선이 실제로 유효하지 않으면 원래 동결 알고리즘을 유지한다.

### C. 과학적 문제

예:
- 원본 입력 결손
- 실제 물리 제약 위반
- 수학적으로 증명된 Infeasibility
- 데이터 시점·인과 경계 오류

이 경우 데이터를 임의 수정하거나 제약을 완화해 통과시키지 않는다.

독립 증거를 확보하고 해당 날짜를 실패 또는 미인증으로 분류한 뒤 캠페인을 계속 진행한다.

## 3. 절대 금지 사항

다음은 자동복구 과정에서도 금지한다.

**메모리 관련**

- Gurobi MemLimit 설정 금지
- SoftMemLimit 설정 금지
- Python/OS 메모리 상한 금지
- RAM 사용량을 근거로 정상 Solver 강제 종료 금지
- 메모리 제한으로 최적화 문제 규모를 강제로 축소하는 조치 금지

CPU/RAM/RSS/Swap 관측은 정보 수집용으로만 사용한다.

**감속 관련**

- 인위적인 sleep 삽입 금지
- CPU 사용률 제한 금지
- 실행 우선순위 강제 하향 금지
- 성능 저하를 유도하는 Throttling 금지
- 불필요한 Solver 재시작 금지

기존 과학적으로 고정된 Threads 설정은 유지한다.

**휴리스틱 및 근사 관련**

- 새로운 Greedy/Random/Search 기반 휴리스틱 도입 금지
- 최적화 실패를 가리는 임의 복구해 생성 금지
- 임의 SOC discretization 금지
- Top-k 경로 축소 금지
- 근거 없는 변수 또는 제약 삭제 금지
- Fractional binary rounding을 통한 인증 금지
- Native Solver의 미인증 bound를 Exact Global LB로 승격 금지

기존 M-stage에 포함된 Adaptive Role-Exchange LNS는 이전에 독립 정수·물리 검증과 Exact Global Gap 인증으로 사용된 기존 알고리즘이다.

해당 기존 알고리즘의 재사용과 신규 미검증 휴리스틱 도입을 구분하라.

기존 LNS의 제한된 이웃에 대한 ObjBound를 원본 Global LB로 사용해서는 안 된다.

기존 Gurobi Heuristics 설정도 별도 감사하라. 기존 frozen 설정과 사용자의 휴리스틱 제한이 충돌하면 이를 명시적으로 기록하고, 과거 결과를 변경하지 않은 별도 정책 버전에서만 검증하라.

**과학적 조건**

- 원본 목적함수 변경 금지
- 전압·선로·변압기 제약 완화 금지
- MESS 경로·이동에너지·SOC·PCS 제약 완화 금지
- AIDC Job/GPU/WAN/서비스량 임의 변경 금지
- QoS 임의 변경 금지
- 미래 데이터 누수 금지
- Gap 기준 완화 금지

## 4. 기존 알고리즘 적극 재사용

B1은 기존 A-stage P1-only 알고리즘이다.

- AIDC 최적화 ON
- MESS OFF
- Gap 0.5%

B2는 기존 M-stage P1-only 알고리즘이다.

- AIDC 최적화 OFF
- MESS ON
- Gap 3%

B2의 AIDC 기준 스케줄은 해당 날짜 원본 입력에서 독립 생성한다.

B0 또는 B1의 실행 결과 스케줄을 B2에 재사용하지 않는다.

기존 A-stage complete pricing, existing integer recovery, original physical checker 및 Exact LP Bound 인증을 재사용한다.

기존 M-stage Primal–Dual Hybrid, 동치 압축 모델, Route/SOC/PQ/PCS 제약 및 Exact LB 검증기를 재사용한다.

동일한 기능의 코드를 새로 개발하기 전에 기존 구현을 확인하라.

## 5. TIME_LIMIT 발생 시 행동

각 날짜·비교군의 최적화+인증 Wall 상한 90분과 Native 누적 90분은 유지한다.

TIME_LIMIT은 반드시 버그를 의미하지 않는다.

TIME_LIMIT이 발생하면:

1. 정수해와 Global LB/Gap의 유효성을 평가한다.
2. 해당 날짜의 원본 로그·증거·Runtime을 보존한다.
3. 미인증이면 정확히 TIME_LIMIT 또는 TIME_LIMIT_FEASIBLE_NOT_CERTIFIED로 분류한다.
4. Coordinator가 다음 날짜로 진행하게 한다.
5. Codex는 병목 원인을 분석하고, 동일 문제가 반복되거나 개선 근거가 있을 때만 코드 개선을 추진한다.

기존 날짜의 90분 예산을 초기화하거나 임의 연장하지 않는다.

개선된 알고리즘으로 과거 실패 날짜를 다시 평가할 필요가 있으면, 기존 결과를 덮어쓰지 않고 **새 알고리즘 버전·새 Attempt ID·새 독립 예산**으로 별도 재검증한다.

재평가를 무한히 반복하지 않는다.

한 날짜의 실패 때문에 B1 31일 전체 또는 B2 31일 전체를 중단하지 않는다.

## 6. 자동 코드 수정과 반영 절차

매시간 문제가 발견되면 다음 순서로 진행한다.

1. 오류의 최초 발생 시점과 원인을 식별한다.
2. 기존 구현 중 재사용 가능한 코드를 찾는다.
3. 최소한의 수정안을 작성한다.
4. 기존 연구·원본 데이터·ledger를 보존한다.
5. 새 수정 코드를 별도 D 드라이브 작업공간 또는 독립 Worktree에서 검증한다.
6. Native=0 회귀 및 원본 문제 동치성 검사부터 통과시킨다.
7. 필요한 경우 별도 유한 Native 검증을 수행한다.
8. 기존 동결 알고리즘 대비 성능 및 인증 결과를 비교한다.
9. PASS한 수정만 별도 commit으로 저장한다.
10. 안전한 실행 경계에서만 다음 날짜 실행기에 반영한다.

### 실행 중인 Solver 코드 변경 금지

현재 Worker가 실행 중이라면 그 Worker의 source hash, model, callback, 파라미터를 바꾸지 않는다.

새 수정 코드는 별도 버전으로 준비하고, 기존 Worker가 정상 종료한 뒤 다음 날짜를 시작하기 전에 Coordinator가 검증된 버전을 선택하게 한다.

Worker는 자신의 시작 시점에 선택된 알고리즘 버전을 끝까지 유지해야 한다.

### 과학적 동일성 보존

알고리즘 수정으로 수학적 모델, 입력, 물리 제약 또는 목적함수가 달라지면 이를 자동으로 동일한 실험으로 처리하지 않는다.

과학적 변경이 불가피하면 변경 전후를 별도 버전으로 분리하고, 사용자 검토가 필요한 항목으로 보고한다.

동치 알고리즘의 코드·성능 개선은 독립 증명과 테스트를 통과한 경우에만 다음 실행에 적용한다.

기존 성공 날짜와 수정 후 날짜를 비교할 때 알고리즘 버전과 실행조건을 기록한다.

버전이 다르면 월간 집계에서 이를 숨기지 않는다. 동일 알고리즘 기준의 월간 통계를 만들려면 필요한 날짜를 별도 재검증 계획으로 관리한다.

## 7. 자동 복구와 재개

Coordinator가 정상 실행 중이라면 건드리지 않는다.

Coordinator가 종료됐다면 OS identity, checkpoint, 실패 원인을 검증한다.

복구 가능한 Infrastructure 오류로 확인되면:

- 기존 checkpoint를 보존
- 완료 날짜 재실행 금지
- 미완료 날짜 확인
- 중복 Worker 존재 여부 확인
- 동일 Run ID/과학적 권한 유지
- 검증된 실행 진입점으로 Coordinator 복구
- 새로운 Heartbeat와 진행 상태 검증

권한 부족, Windows 로그오프, 절전 또는 애플리케이션 종료 등으로 실제 복구가 불가능하면 해결되지 않은 상태를 명확히 보고한다.

관리자 권한을 무단 우회하거나 시스템 보안 정책을 변경하지 않는다.

Codex 예약이 중지되더라도 Windows Coordinator는 독립적으로 실행돼야 한다.

## 8. B1→B2 자동 전환 확인

B1의 31일이 모두 정상적인 종료 상태에 도달하면, 실패 날짜가 있더라도 B2를 자동 시작한다.

B2는 반드시 May01부터 시작한다.

- B1 일부 날짜 미완료: B2 시작 금지
- B1 31일 종료: B2 시작 허용
- B1에 TIME_LIMIT/FAIL 포함: B2 시작 허용
- 전환 중 오류: checkpoint에서 안전하게 복구
- B1/B2 ledger와 원본 입력 혼용 금지

매시간 상태를 확인하되, **전환 자체는 OS Coordinator가 처리**한다.

B1→B2 전환을 위해 다음 Codex 예약 실행까지 기다리지 않는다.

전환 시점·B2 Worker PID·SHA·Heartbeat를 자동 기록한다.

## 9. Codex 예약 자동화 설정

Codex에서 다음 설정으로 예약 자동화를 실제 생성하라.

- 제목: `V42 May B1-B2 Hourly Recovery`
- 실행 주기: 매 1시간
- 프로젝트: `D:\MobileESS_v42`
- 자동화 종류: 독립 실행되는 반복 작업
- 실행 내용: 본 지시문의 매시간 검사·분석·복구 절차
- 시작: B1/B2 캠페인 실제 실행이 확인된 후
- 종료 조건: 62개 arm/date가 모두 종료되고 미처리 복구 작업도 없는 경우

자동화에서 작업 실행 시 이전 예약 작업이 아직 실행 중이면 중복으로 시작하지 않는다.

자동화 자체의 Lock과 PID identity를 확인하라.

한 번의 점검에서 해결하지 못한 항목은 다음 점검으로 전달할 수 있도록 지속적인 `MAINTENANCE_STATE.json`을 기록한다.

해결되지 않은 항목을 매시간 처음부터 조사하지 않는다.

예약 자동화가 실제로 생성·활성화됐는지 확인하고, 최초 실행을 테스트하라.

Codex 데스크톱 앱과 로컬 프로젝트 접근이 유지되어야 예약 실행이 가능하다는 사실을 기록한다.

Codex 예약 기능이 현재 환경에서 사용 불가능하면 이를 정확히 보고하고, 예약이 성공했다고 주장하지 않는다.

- 발견한 신규 오류
- 원인 분석
- 코드 수정 여부
- 수정 전후 Git SHA
- 테스트 결과
- 원본 모델 동치성
- 검증된 성능 개선
- 실제 재개 여부
- 다음 점검 필요사항

모니터 화면에서도 마지막 Codex 점검 시각과 자동복구 상태를 읽기 전용으로 표시한다.

## 11. Git 정책

기존 연구 원본과 ledger는 변경하지 않는다.

검증된 수정만 `v42`에 반영한다.

- Force push 금지
- 과거 결과 덮어쓰기 금지
- Source/Case/Run SHA 추적
- 원본 과학적 동치성 검증
- 회귀 테스트 PASS
- 기존 PR189 활용
- 활성 Worker source 변경 금지

수정 코드가 검증되지 않으면 자동 승격하지 않는다.

## 12. 최종 운영 지시

**앞으로 Codex는 매시간 다음을 반복한다.**

상태 검사
→ 신규 오류 탐지
→ 원인 분석
→ 기존 코드 재사용
→ 필요한 코드/알고리즘 수정
→ 독립 검증
→ 안전한 배포 및 Coordinator 재개
→ 다음 예약 점검

정상 상태라면 불필요하게 소스·Solver·Coordinator를 수정하지 않는다.

TIME_LIMIT은 결과를 보존하고 다음 날짜로 넘어간다.

메모리 상한, 인위적 감속, 신규 휴리스틱, 물리 제약 완화, 과거 예산 초기화는 금지한다.

**전체 B1 31일→B2 31일의 캠페인이 종료되고 복구 대기 항목이 없어질 때까지 1시간 주기 점검을 유지하라.**

기존 정상 Solver를 중단하지 않으면서, 검증된 수정이 필요한 경우에만 자동 개선·복구·재개하라.
