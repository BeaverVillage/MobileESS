remaining_runtime_proxy

============================================================
4. RUNNING-JOB SEMANTICS
============================================================

Do NOT train a separate remaining-runtime model in this task.

Given frozen total-runtime prediction T_hat_j
and causal observed elapsed execution e_j:

if:

e_j < T_hat_j

then:

R_proxy_j = T_hat_j - e_j

If:

e_j >= T_hat_j

and the real job is still RUNNING:

OVERRUN = TRUE

R_proxy_j must NOT become a fake negative runtime.

The job continues executing.

Requested walltime may remain as a hard maximum request envelope if
source-backed, but:

requested_walltime - elapsed

must NOT be called expected remaining runtime.

============================================================
5. IMPORTANT QUANTILE CAVEAT
============================================================

Document explicitly:

Q90(T | x) - elapsed

is a fixed submit-time residual proxy.

It is NOT mathematically identical to:

Q90(T - elapsed | T > elapsed, x)

because survival to the checkpoint provides additional information.

Do not hide this distinction.

However, do NOT build a second remaining-runtime model unless the diagnostics
in this task demonstrate that the simple proxy is operationally inadequate.

============================================================
11. WHY Q90 IS PRIMARY
============================================================

The scheduling trade-off is:

underprediction
-> runtime overrun
-> unexpected GPU occupancy / downstream conflicts

overprediction
-> inflated reservation
-> artificial queueing
-> jobs pushed beyond the D-day electrical horizon

Therefore evaluate calibration AND sharpness.

The model must not solve underprediction by simply recreating walltime-scale
reservations.

35. MOST IMPORTANT DESIGN PRINCIPLE
============================================================

Keep the architecture simple:

ONE total-runtime ML package.

D-1 known PENDING:
    total-runtime Q90 -> scheduling duration

D-1 known RUNNING:
    same frozen total-runtime prediction
    minus causal elapsed
    -> remaining proxy / OVERUN if exceeded

D-day unknown at submit:
    total-runtime Q90 -> scheduling duration

D-day unknown while RUNNING:
    same total prediction
    minus observed elapsed

No second remaining-runtime ML unless evidence proves it is necessary.

Runtime is an EXOGENOUS prediction.

Runtime is NEVER an optimization variable.

The later V42 controller decides:
- start
- site
- migration

using the frozen runtime estimate.
