# 1. V44_iteration2를 현재 Stage 종료 지점에서 안전 중단

**V44_iteration2는 현재 5월 1일 Planning Stage를 실행 중이라고 사용자에게 보고됐다.**

먼저 실제 로컬 Runtime을 조사하여 다음을 확인하라.

- 현재 날짜와 Stage: M2/A3/M3/A4/M4 중 무엇인지
- Worker PID 및 Process Creation Time
- 실제 Gurobi Native Call 진행 여부
- Native Runtime 사용량과 남은 예산
- Stage Checkpoint
- Supervisor PID 및 OS Lock
- Pending Stage와 자동 재시작 경로

GitHub에 저장된 과거 상태를 현재 실행 상태로 간주하지 않는다.

## 중단 방법

**현재 진행 중인 Stage는 정상 완료될 때까지 유지한다.**

- 실행 중인 Gurobi Solver 강제 종료 금지
- Worker Kill 금지
- Native Call 도중 종료 금지
- Stage 부분 결과를 완료 결과로 변경 금지
- Checkpoint·원장 초기화 금지
- 다음 Stage를 미리 시작하는 것 금지

현재 Stage가 완료되면:

1. Stage 결과 저장
2. 독립 FULL 수용 결과 확인
3. Native Runtime 원장 정리
4. In-flight Call이 없는지 확인
5. Checkpoint와 SHA 동결
6. Supervisor가 **다음 Stage를 시작하지 못하도록 중단**
7. Supervisor·Worker 소유 자원과 OS Lock 정상 해제
8. `PAUSED_FOR_V2_ADD` 상태 기록

예를 들어 현재 A3가 실행 중이면 A3가 끝나는 즉시 정지하고 M3를 실행하지 않는다. 현재 M2라면 M2가 끝나는 즉시 정지한다.

**5월 1일 전체 Planning 완료까지 실행하는 것이 아니다. 지금 실행 중인 Stage 하나만 마무리한다.**

현재 Stage가 이미 종료됐다면 다음 Stage를 실행하지 않고 즉시 안전 중단한다.

### 중요한 Supervisor 조건

현재 실행 중인 Python Supervisor가 일시중단 신호를 실제로 읽는지 확인하라.

소스에 일시중단 조건을 추가하기만 하면 이미 실행 중인 Python 프로세스에 자동 반영된다고 가정하지 않는다.

가능한 기존 제어 인터페이스를 우선 사용하고, 필요한 경우 안전한 Stage-Boundary Pause를 구현하라.

**다음 Stage의 자동 시작을 확실히 차단할 수 없으면 중단 성공을 선언하거나 V2_add를 동시에 시작하지 않는다.**

중단 후 V44_iteration2가 자동으로 다시 시작되지 않도록 영속적인 Hold 상태를 유지한다.

기존 실행 결과와 PR #237의 코드는 보존한다.

## 적용 범위

이 예산 변경은 **V2_add에만 적용**한다.

기존 V44 r043과 V44_iteration2의 Source/Budget은 변경하지 않는다.

다음 항목을 모두 검사하라.

- `stage_handlers.py`의 A-stage 예산
- M-stage StageBudget 생성자

- `mess_stage_budget_seconds`
- Stage Checkpoint와 재개 검증
- `Native_ceiling_seconds`
- `resume` 및 `reconciled`의 기존 900초 비교
- K48와 Joint의 독립 원장
- 각 Solver 실제 `TimeLimit`
- 실행 승인 및 인증 SHA

하드코딩된 5,400/900초 값이 실제 실행 경로에 남아 있는지 전수 조사한다.

기존 원본 알고리즘이나 Solver 내부 정책을 새 알고리즘으로 교체하지 않는다.

- 신규 Grid Constraint Generation

**개선 효과가 없거나 메모리·시간이 오히려 증가하는 변경은 채택하지 않는다.**

# 5. 실행 전에 기존 결함 전부 해결

## 5.1 AIDC 시작시간 Domain 결함

현재 PR #236에서 확인된 차이:

- 전체 Job: 1,499개
- 영향받은 Job: 1,395개
- 원본 r043에서 허용하던 추가 `physical_starts`: 121,313개
- V2_add Adapter는 입력 `WINDOWS`와 교차 제한

이 문제를 반드시 재검토하라.

다음 항목을 독립 검증한다.

1. 원본 r043 `physical_starts`의 정확한 수학적 의미
2. 입력 `WINDOWS`의 Source Authority
3. Known/Unknown Job 시간 제약
4. QoS/Deadline과 사전 실행 허용 조건
5. Pre-site/Time-shifting/Migration 가능 영역
6. 제외된 121,313개 시작 선택의 실제 물리적 유효성
7. 기존 IEEE123과 IEEE8500의 비교 가능성

원본에서 유효했던 Job 시작 선택을 정당한 근거 없이 제거해서는 안 된다.

반대로 실제 입력 WINDOW를 위반하는 시작 선택을 무조건 되살리는 것도 금지한다.

**어느 도메인이 과학적으로 권위 있는지 확정하고, Source의 의도와 일치하는 올바른 도메인으로 수정하라.**

수정 후 전체 Job/Capacity/QoS/Deadline/Carryout 검증을 다시 실행한다.

시작시간 Domain 변경으로 원본 r043과 수학적 문제가 달라진다면 해당 차이를 명확히 인증하고, 허용되지 않은 차이를 원본과 완전 동등하다고 주장하지 않는다.
