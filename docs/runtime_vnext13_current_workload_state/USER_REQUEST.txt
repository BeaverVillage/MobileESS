============================================================
0. WHY V13 EXISTS
============================================================

Runtime-vNext12 tested the hypothesis:

    job descriptors
    + recent completed-job runtime regime
        ->
    better temporal runtime prediction

The hypothesis was NOT supported.

V12 results:

R0 static baseline:
    pooled Q90 = 91.74%
    min fold = 66.47%
    >4h = 71.07%

R2 with global + cohort completed-runtime regime:
    pooled Q90 = 89.16%
    min fold = 52.04%
    >4h = 51.97%

Recent completed-runtime history did not consistently predict the next
workload regime.

Important V12 forensic finding:

    recent completed jobs may react too slowly to a newly arriving
    workload wave.

Example conceptual situation:

At time t:
    hundreds of large jobs may have just been submitted,
    but none has completed yet.

Therefore:
    completed-runtime features still describe the previous regime,
    while the current workload composition has already changed.

V13 tests a different hypothesis:

    The runtime regime may be better represented by CURRENT observable
    submission / queue / running state than by recently completed runtimes.

============================================================
4. CRITICAL IMPLEMENTATION RULE:
EVENT-SOURCED CAUSAL STATE
============================================================

Do NOT reconstruct current state by directly asking future-aware questions such
as:

    end_time > t
    start_time > t

from the complete archive row.

Even if logically equivalent retrospectively, this can accidentally expose
future timestamps.

Instead construct a chronological EVENT STREAM.

Events may include, when supported:

SUBMIT event
START event
END event

At replay timestamp t:

- events with timestamp < t have been processed
- events with timestamp >= t have NOT been processed

The current state must be derived only from processed events.

For prediction of job j at its prediction event time:

    process all strictly earlier events
    do NOT process j's own future START or END

Define exact same-timestamp ordering explicitly.

============================================================
5. SAME-TIMESTAMP EVENT ORDER
============================================================

Freeze a deterministic order before model evaluation.

Conservative proposed order at identical timestamps:

1. END events strictly before the prediction event only
2. prior START events
3. prior SUBMIT events
4. prediction event for current job
5. no simultaneous/future event belonging to the current job

Alternatively use stable source event sequence if source authority provides it.

Do NOT invent ordering after observing performance.

Required:

SAME_TIMESTAMP_EVENT_CONTRACT.json

============================================================
7. ARRIVAL PRESSURE FEATURES
============================================================

At prediction time t construct, using already observed submissions only:

Windows:

    15 min
    1 h
    6 h
    24 h

Candidate features:

- submit_count
- submitted_requested_GPU_sum
- submitted_requested_nodes_sum
- submitted_requested_cores_sum
- submitted_requested_memory_sum

- requested_GPU_time_sum
    = requested_GPU * requested_walltime
  where both research proxy values are valid

- mean / median requested GPU
- mean / median requested walltime
- Q75 / Q90 requested walltime

- high_GPU submission fraction
- long_requested_walltime fraction
- array-job fraction

Do not use actual runtime.

============================================================
8. BURST / CAMPAIGN FEATURES
============================================================

A workload wave may appear as a burst.

Construct causal descriptors such as:

- submissions in last 5/15/60 min
- inter-arrival time of current job
- time since previous submit
- number of jobs sharing same submit timestamp
- recent array-job submission count
- recent large-GPU submit count

If stable anonymized account is used:

- same-account submissions in last 1h / 6h

If partition/QoS is present:

- same-partition recent submits
- same-QoS recent submits

Do NOT use job IDs as predictive lookup keys.

============================================================
9. CURRENT PENDING / QUEUE STATE
============================================================

Using the event-sourced state machine, at time t:

PENDING =
    SUBMIT observed
    but START event not yet observed

Construct:

- pending_job_count
- pending_requested_GPU_sum
- pending_nodes_sum
- pending_requested_GPU_time_sum
- pending_walltime_q50/q90
- pending_GPU_q50/q90

Composition:

- pending QoS shares
- pending partition shares
- pending GPU-size bucket shares
- pending walltime-bucket shares

Age:

- pending_age_q50
- pending_age_q90
- maximum pending age

Pending age may be computed from the observed archive submit timestamp under the
existing Kestrel_trace_proxy limitation.

Do not read future START timestamp.

============================================================
10. CURRENT RUNNING STATE
============================================================

RUNNING =
    START event already observed
    and END event has not yet been observed in the event stream

Construct:

- running_job_count
- running_requested_GPU_sum
- running_nodes_sum
- running_cores_sum
- running_memory_sum

Execution age:
- running_elapsed_q50
- running_elapsed_q90
- max running elapsed

Composition:
- running QoS shares
- running partition shares
- running GPU-size bucket shares

Important:

running elapsed must be:

    prediction_time - observed_start_time

for jobs whose START event was already processed.

Do NOT read their future end time.
