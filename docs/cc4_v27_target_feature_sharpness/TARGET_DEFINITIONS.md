# CC4-v2.7 타깃·시간 경계 계약

모든 날짜는 고정 UTC+10 모델 시계다. 예측 발행은 D-1 18:00이며 시간 구간은 왼쪽 포함·오른쪽 제외다. 경계 제출 조건은 엄격한 `submit > issue`다. 발행 시각과 같은 시각의 제출은 알려진 모집단에 속한다.

* T0: 기존 적격 GPU 작업의 D일 제출 시간에 요청 GPU × 전체 실현 실행시간을 모두 배정한다. 14:20 제출, 4 GPU, 2.5시간 실행 작업은 14시 빈에 10 GPUh를 기여한다. 실행 구간에 분산하지 않는다.
* T1: T0와 같은 작업·제출 시간 모집단에 요청 GPU만 합한다. 런타임 곱 효과를 분리하는 도착량 진단이며 전력 타깃으로 승격하지 않는다.
* T2: 발행 후 제출한 작업의 실제 실행 `[start,end)`와 D일 각 시간의 교집합 길이에 요청 GPU를 곱한다. 단위는 시간당 GPUh이며 평균 활성 GPU와 수치상 같다. 이전 날 18시~자정 제출도 포함한다.
* T3: T2와 동일한 작업의 15분 교집합 GPUh를 계산한다. 예측 타깃은 그 값의 4배인 평균 활성 GPU다. 일 적분량과 예측 적분량 계산에는 반드시 0.25시간을 곱한다. 시간별 T3 평균은 T2와 같다.

적격 작업은 기존 기준 그대로 유한한 양의 GPU 요청, 존재하는 시작·종료, `submit <= start < end`를 만족한다. 미완료·시간 오류 작업은 별도 집계하며 부하가 0이라고 주장하지 않는다. 본 결과는 이 역사적 실현 라벨 모집단에 조건부다. T2/T3의 참조 정합성 1은 정의에 따른 항등식이며 모델의 예측 성공을 뜻하지 않는다. 실제 정책에 따라 실행 시각은 바뀔 수 있으므로 이 자료만으로 V42 정책 변경 후 실행 궤적을 보장할 수 없다.

T0 전체 일 라벨의 성숙 시각은 기존 DAY_LEDGER와 정확히 일치해야 한다. T1은 동일 적격 모집단의 판정이 필요하므로 보수적으로 같은 완료 성숙 조건을 쓴다. T2/T3는 `(historical issue, D end)` 제출의 완료 시각과 D 종료 중 늦은 시각까지 기다린다. 해당 구간에 종료 미확인 양의 GPU 작업이 있으면 전체 일 라벨을 미성숙으로 둔다. 이는 실시간 점유 관측을 가정하지 않는 보수적 계약이다. 재학습은 전체 일의 성숙 시각이 발행보다 엄격히 이전일 때만 허용한다.

F1에서 T0/T1은 각 과거 제출 빈의 종료·적격 판정 성숙을 사용한다. T2/T3는 위 전체 일 성숙을 사용한다. 따라서 과거 1일 동일 시각 값도 아직 성숙하지 않았다면 결측 마스크로 제외한다. 값 0과 실제 관측 0은 가용성 마스크로 구별한다. 실제 start/end는 라벨 및 성숙 여부 판정에만 사용한다.

F0 71개 값은 모든 타깃에서 비트 단위로 보존한다. T3에서는 같은 시간의 네 슬롯에 원래 값들을 반복하고 슬롯·시각·분 단위 리드타임 3개 결정론적 열만 추가한다. F3는 입증된 과거 스냅샷이 없어 NOT_AVAILABLE이며 F0와 동일하다. F4에는 요일·월·계절 범주만 추가한다. UTC+10 모델 시계로 공휴일 관할을 추정하지 않는다. F2는 완료 적격성을 보지 않고 발행 이전의 양의 GPU 요청 이벤트만 사용한다. 과거 요청값 버전 및 수집 지연 미검증이라는 기존 제한은 그대로 남는다.

기존 DAY_LEDGER는 변경하지 않는다. OOS_EXTENSION 63일은 원래 eligible=False라는 정보를 보존하면서 사용자 요청의 별도 확장 평가로만 보고한다. 개발·보정·제외·기존 평가·5월 역할은 재설계하지 않는다. 5월은 노출된 역사적 진단이다.

원시 출력과 보정 출력을 분리한다. 주변 슬롯 Q90의 합은 공동 일 Q90이 아니며 적분 reserve/sharpness 대용량이다. 서로 다른 단위의 T0/T1/T2/T3 손실이나 요구량 비율을 직접 순위화하지 않는다. 각 타깃의 F0를 기준으로 특징 효과를 비교한다. PCC 변환은 권한 있는 결정론적 입력·매핑이 확보되지 않아 추가하지 않는다.
