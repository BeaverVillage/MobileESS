## 1. Unknown Reference 시작시각 결함 수정

현재 코드:

- `v43_actual/case.py`
- `v43_actual/vendor/qos.py`
- `CausalReferenceScheduler`

에서 미래 Known Job의 마지막 시작시각이 Unknown 전체의 `last_pending_start_seconds`에 반영되는 구조를 수정하라.

### 수정 원칙

1. Known Job의 미래 Site/Start/예약은 유지한다.
2. 특정 Known의 미래 시작시각을 모든 Unknown의 전역 시작 하한으로 사용하지 않는다.
3. Unknown은 실제 Submit 이후 가장 이른 합법적인 시작시각을 탐색한다.
4. 각 사이트의 실제 GPU 예약·미래 Known 예약·이미 확정된 Unknown 예약은 정확하게 고려한다.
5. FIFO는 작업 처리 순서의 공정성으로 유지하되, 서로 다른 사이트에 빈 GPU가 있어도 전역 시간 장벽 때문에 모두 대기하는 현상은 제거한다.
6. 미래 실제 완료시간이나 향후 도착할 Unknown UID를 사용하지 않는다.

예를 들어 Known이 IDC03에서 22:00에 시작하도록 예약됐더라도, 09:00에 도착한 Unknown이 IDC05에서 GPU/Rack/계통 제약을 충족하면 09:00에 시작할 수 있어야 한다.

기존 Known 예약을 삭제하거나 Unknown이 Known의 예약 용량을 선점해서는 안 된다.

최소한 다음 회귀 테스트를 추가한다.

- 미래 Known 시작시각에 의한 잘못된 전역 대기
- 서로 다른 사이트에서의 동시 실행 가능성
- 동일 사이트의 예약 충돌
- Running Overrun의 실제 GPU 점유 유지
- FIFO·QoS·Deadline
- 미래 Unknown 정보 차단
- CC4 이중 계상 방지

원본 PR189 Planning 최적화 코드는 변경하지 않는다.

## 2. Unknown 849개 미실행 원인 분석 및 해결

기존 실제 보고에서 다음이 확인됐다.

- Unknown UID: 849
- Started: 0
- Completed: 0
- Compute: 0 GPUh
- 초기 Reference 시작: 22:00
- `CURRENT_OBSERVED_ORIGINAL_PLANNING_VOLTAGE`: 3,485회
- `PHYSICAL_CAPACITY_RUNNING_RETAINED`: 17회
- `NO_CAPACITY`: 4회

위 수치는 반복 이벤트 건수이지 서로 다른 UID 수가 아니다.

### 필수 분석

기존 원장을 수정하지 않고 다음을 독립적으로 분석하라.

1. 시작시각 결함 제거 시 얼마나 많은 Unknown이 앞당겨지는가?
2. UID별 최초 차단 원인은 무엇인가?
3. 전압 검사에서 거부된 후보의 실제 사이트·시간·상·전압 제약은 무엇인가?
4. 원본 Signed Affine 모델과 실제 OpenDSS Current AC 판단이 일치하는가?
5. 실제 물리적으로 가능한 배치도 보수적인 전압 검사 때문에 거부된 것은 아닌가?
6. GPU/Rack 예약 및 QoS 충돌이 독립적인 원인인가?

일부 실제 상태와 후보에 대해 원본 선형 모델과 독립 Current AC를 대조하라.

**정당한 물리적 위반은 절대 완화하지 마라.**

다만 보정모델의 거부가 실제 물리 위반과 불일치하는 것으로 증명되면, 그 원인을 수정하고 별도 Actual Policy 버전으로 독립 검증하라.

검증 없이 전압 하한, 선로 정격, GPU 용량 또는 Solver Tolerance를 변경하는 것은 금지한다.

849개를 인위적으로 실행시키거나 완료 처리하지 마라.

## 3. R1-FLEX30 연구 가정 도입

기존 Strict Source 결과는 보존한다.

새로운 연구용 정책을 별도로 추가한다.

- `R1-FLEX30-C0`
- `R1-FLEX30-C1`

### 참여 대상

- 실제 관측된 Unknown Job
- 상태가 PENDING
- 호환 가능한 대체 AIDC가 존재
- Protected/Urgent 등 이동 금지 대상 제외
- 명시적인 Source 목적지 금지 조건 보존
- 원본 GPU/Rack/QoS/Deadline 만족

위 조건으로 정의한 적격 Unknown 중 **약 30%에 Pre-site 참여 권한을 가정**한다.

### 참여자 선택

미래 전체 Unknown UID 목록을 사전에 읽어 정확히 30%를 선택하지 마라.

대신 고정된 Seed와 UID 기반의 결정론적 Hash를 사용하여 **Job 도착 시에만** 참여 여부를 결정한다.

이 선택은 C0/C1과 B0/B1/B2/B3에서 동일한 규칙을 사용한다.

관측된 실제 참여율과 GPUh 비율을 각각 기록한다.

### 권한 가정

R1 참여자에게 다음을 연구 가정으로 부여한다.

- 실행 전 호환 AIDC로 배치 변경 허용
- 허용된 목적지의 입력 데이터가 사전 준비된 것으로 가정
- 사전 준비 시 추가 실시간 WAN 전송이 없다는 가정을 명시

이 권한은 `R1_ASSUMED`이지 `SOURCE_VERIFIED`가 아니다.

명시적으로 금지된 Destination은 허용하지 않는다.

필요한 데이터 전송을 사전 준비했다고 가정하지 않는 사례에서는 실제 WAN 경로·대역폭·전송시간을 검증하라.

RUNNING Migration과 별도의 의도적 Time-shifting 권한은 부여하지 않는다.

### C0/C1 공정성

R1-FLEX30-C0와 R1-FLEX30-C1은 동일한 참여 UID, 자원조건, Known Planning, 실제 작업 도착, QoS, 전력망 모델을 사용한다.

- C0: 기본 사이트를 사용하며 Pre-site 제어는 하지 않음
- C1: 동일한 적격 집합에서 민감도 기반 Pre-site 선택

참여 권한 자체가 C0의 부하 또는 서비스량을 다르게 만들면 안 된다.

## 4. Overrun-Triggered Unknown Corrective Pre-site 구현

새 Actual 정책의 핵심이다.

**Known은 계획 유지, Unknown만 Corrective Pre-site 허용**한다.

### 4.1 Overrun 관측

Observed RUNNING Job이 현재 시점에도 실행 중이고, 관측된 실행 시작·경과시간과 공개된 Q50 기준의 명목 완료시각을 넘어섰다면 Overrun으로 기록한다.

미래 실제 Runtime이나 완료시각을 Controller에 제공하지 않는다.

Overrun이 발생한 Job의 현재 GPU 점유는 실제 완료·해제 이벤트까지 보존한다.

### 4.2 Pre-site 재평가 Trigger

다음 이벤트에서 아직 PENDING인 Unknown을 평가한다.

1. Unknown Job이 실제 도착한 시점
2. Overrun이 관측되어 기본 사이트의 실행이 차단된 경우
3. GPU 점유 또는 예약 상태가 변경되어 기존 대기 Job의 실행 가능성이 달라진 경우
4. 대기가 계속되는 동안의 15분 제어시각

한 번 QUEUE 처리된 Unknown이 이후에도 무기한 QUEUE 상태에 고정되지 않도록 재평가한다.

동일 시각 동일 상태에서 불필요한 중복 평가를 하지 않는다.

### 4.3 Known 처리

Known Job은 최종 Planning 명령을 그대로 유지한다.

- 기존 Allocation 유지
- 기존 Time-shifting 유지
- 기존 승인된 Planned Migration 유지
- 새로운 Corrective Pre-site 금지
- 새로운 Actual Time-shifting 최적화 금지
- Overrun으로 용량이 부족하면 계획된 사이트에서 대기
- Actual 실행 지연과 QoS 위반을 기록

기존 Known 명령, 최종 UID 계획, 원래 예약의 Source는 수정하지 않는다.

단, 실제 Overrun으로 실행이 지연되는 경우 현재 점유와 예약을 안전하게 갱신한다.

### 4.4 Unknown 후보 선택

Overrun 때문에 기본 사이트에서 시작할 수 없는 Unknown에 대해:

1. 원래 기본 사이트 실행 가능성 검사
2. R1-FLEX30 참여 권한 검사
3. 대체 호환 사이트 탐색
4. 현재 GPU/Rack/WAN/예약 검사
5. QoS·Deadline 검사
6. 원본 Signed Sensitivity로 후보 평가
7. 실제 Current AC로 최종 안전성 확인
8. 원자적으로 GPU 예약 후 실행

모든 후보에 실제로 불가능한 제약이 존재하면 QUEUE 유지한다.

기본 사이트가 불가능해도 다른 사이트가 실제로 가능하다면, 불가능한 기본 사이트의 가상 점수와 비교해서 대안을 거부하지 마라.

가능한 후보 중 최대 선로·상 부하율 및 부하 누적 영향을 낮추는 후보를 선택한다.

기본 사이트도 실행 가능하다면 이동은 실제 전력망 지표 개선 또는 명확히 정의된 서비스 회복 이득이 있을 때만 선택한다.

민감도는 후보 순위화에 사용하고, 최종 실행은 Current AC 하드 제약을 통과해야 한다.

### 4.5 절대 금지

- Known의 새로운 Pre-site
- RUNNING Job 강제 중단·퇴거
- RUNNING Job의 새 Migration
- 미래 실제 완료시간 활용
- 계획되지 않은 MESS P/Q 변경
- Actual Global MILP
- 전압·선로 제약 임의 완화
- 다른 UID의 확정 예약 자동 취소
- 동일 UID의 중복 GPU 예약
- 동일 Unknown의 CC4 중복 차감

Overrun과 Pre-site의 모든 결정은 현재 관측 상태와 동결된 정책만으로 수행한다.

## 8. May01 최종 비교 시나리오

각 Arm에 대해 최종적으로 다음 두 정책을 실행한다.

- `R1-FLEX30-C0`
- `R1-FLEX30-C1`

총 **4 Arm × 2 Actual 정책 = 8개 Actual96·Fresh96 결과**를 목표로 한다.

기존 Strict C0/C1은 역사적 보수적 대조 결과로 별도 보존한다.

두 R1 정책은 동일한 Source/Case, 실제 Known·Unknown 이벤트, 참여자 선택, QoS, C1 전력모델, 원본 IEEE123·7-RegControl 하드웨어를 사용한다.

기존 B0 Attempt002가 정상 종료되면 그 결과를 보존하고, 수정된 Actual Policy는 별도 Attempt에서 재검증하라.

최종 비교에서 반드시 다음을 계산한다.

1. B1−B0: AIDC 최적화 효과
2. B2−B0: MESS 최적화 효과

4. B3−B2: 공동최적화 추가 효과
5. 각 Arm에서 R1-FLEX30-C1 − R1-FLEX30-C0: Unknown Corrective Pre-site 효과
