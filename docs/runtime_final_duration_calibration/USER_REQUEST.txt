============================================================
1. PRIMARY RUNTIME RATIO — EXACT DEFINITION
============================================================

For each job j:

    T_j     = realized runtime in seconds
    Q50_j   = frozen predicted median runtime in seconds
    Q90_j   = frozen predicted upper-quantile runtime in seconds

Define:

    TIME_RATIO_Q50 =
        sum_j Q50_j
        /
        sum_j T_j

    TIME_RATIO_Q90 =
        sum_j Q90_j
        /
        sum_j T_j

These are aggregate runtime-duration ratios.

DO NOT multiply by requested GPUs.

DO NOT call these GPU reservation ratios.

Interpretation example:

    TIME_RATIO_Q90 = 2.0

means:

    the sum of predicted Q90 runtimes is twice the sum of realized runtimes.

It does NOT mean every individual job is predicted as exactly 2x longer.

============================================================
2. ALSO REPORT PER-JOB RATIO DISTRIBUTION
============================================================

For jobs with T_j > 0 calculate:

    r50_j = Q50_j / T_j
    r90_j = Q90_j / T_j

Report:

    median
    Q25
    Q75
    Q90
    mean only as a diagnostic

for both r50 and r90.

The aggregate ratio and median job-level ratio must be kept separate.

Do NOT allow zero-runtime rows to create infinite ratios.
Report zero-runtime rows separately.

============================================================
7. IMPORTANT — Q50 MAE AND Q90 COVERAGE HAVE DIFFERENT ROLES
============================================================

Q50 MAE:

    point/median runtime accuracy

Q90 coverage:

    upper-bound reliability

Do NOT use Q90 MAE as the primary accuracy metric.

A good upper quantile is intentionally above many realized runtimes,
so Q90 MAE can penalize useful conservatism.

============================================================
8. OPERATIONAL DURATION — Q50/Q90 CALIBRATION
============================================================

Do NOT automatically hard-reserve every job to Q90.

Construct an operational duration:

    T_op_j(alpha)
        =
        Q50_j
        +
        alpha * (Q90_j - Q50_j)

with:

    0 <= alpha <= 1

Interpretation:

    alpha = 0 -> pure Q50
    alpha = 1 -> pure Q90

This is a scheduling-duration calibration,
NOT a new ML model.

Do not call T_op a Q90 unless alpha=1.

Call it:

    CALIBRATED_OPERATIONAL_RUNTIME

============================================================
10. ALPHA SELECTION RULE
============================================================

The purpose is NOT to force a 1.x ratio.

For each candidate on CAL:

find alpha values whose empirical operational-duration coverage is
closest to the nominal 90% reliability reference.

Primary selection:

    among alpha values with CAL coverage >= 0.90,
    choose the alpha with the lowest TIME_RATIO_OP.

If no alpha achieves CAL coverage >= 0.90:

    choose the alpha with the highest CAL coverage,
    and mark:

        CAL_90PCT_UNATTAINABLE = TRUE

Do NOT lower the target to 85%.

Do NOT select alpha based on VALID.

============================================================
11. OPERATIONAL TIME RATIO
============================================================

After alpha is frozen, evaluate on VALID:

    TIME_RATIO_OP =
        sum_j T_op_j
        /
        sum_j T_j

Again:

    NO GPU WEIGHTING.

Also compute:

    T_OP_COVERAGE =
        fraction(T_j <= T_op_j)

    min-fold T_OP_COVERAGE

    >4h T_OP_COVERAGE
    >12h T_OP_COVERAGE
    >24h T_OP_COVERAGE

============================================================
13. WHY THIS IS BETTER THAN GPUH FOR FINAL RUNTIME SELECTION
============================================================

The Runtime model predicts:

    runtime seconds

Therefore intrinsic model conservatism should first be measured by:

    predicted runtime seconds
    /
    realized runtime seconds

GPUh additionally weights jobs by requested GPU count and answers a
different downstream question.

That downstream effect will be measured only after the Runtime model is
integrated with the V42 scheduler.

Do not conflate the two.
