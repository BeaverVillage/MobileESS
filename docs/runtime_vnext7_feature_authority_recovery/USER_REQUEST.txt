IMPORTANT:
DO NOT train or select a new production runtime model yet.

The immediate goal is to recover and prove a source-backed set of
JOB-SPECIFIC FEATURES that were actually available at job submission time.

Only AFTER this feature authority is frozen may a later task retrain Runtime ML.

============================================================
0. WHY THIS TASK EXISTS
============================================================

Runtime-vNext6 failed primarily because all informative request fields were
excluded under the strict causal feature policy.

The selected strict model therefore had:

job-specific feature count = 0

and effectively predicted the same unconditional runtime distribution for
every job.

This produced:

- Q90 around 15.55 h for every job
- April overall Q90 coverage 95.67%
- >4 h job coverage only 77.66%
- April reservation/actual GPUh about 4.136×
- only 3.85% reservation reduction relative to walltime
- April-2 start>=H worsening from 2190/2340 to 2340/2340
- checkpoint subtraction diagnostic failure

Do NOT attempt to fix these outcomes by:
- changing quantile
- increasing model complexity
- adding neural models
- adding survival models
- tuning on April

First recover informative causal features.

============================================================
1. PRIMARY SCIENTIFIC QUESTION
============================================================

Determine:

"Which Kestrel job/request fields can be proven to represent information
available at the ORIGINAL job submission time, rather than a later or final
scheduler/accounting state?"

The final output must classify every candidate feature as:

A. VERIFIED_SUBMISSION_TIME
B. VERIFIED_IMMUTABLE
C. OBSERVABLE_AT_SUBMIT_BUT_MUTABLE_WITH_VERSION_HISTORY
D. PRESENT_IN_ARCHIVE_BUT_VERSION_UNRESOLVED
E. POST_SUBMISSION
F. OUTCOME / LABEL ONLY
G. UNSUPPORTED / UNKNOWN

Only categories A/B, or C with a reconstructable correct historical version,
may be candidates for production Runtime ML.

============================================================

no observed modification

is NOT proof that the archive value is the original request.

For each field distinguish:

scheduler capability
vs
observed Kestrel behavior
vs
published dataset semantics
vs
provenance authority.

============================================================
21. STOP CONDITIONS
============================================================

Stop rather than guessing if:

- original request version cannot be reconstructed,
- request fields are only final accounting values,
- source code cannot establish publication semantics,
- duplicate/requeue identities are ambiguous,
- a proposed feature requires future execution information,
- a workflow identifier risks deanonymization,
- no informative strict feature remains.

Do not loosen the causal standard simply to obtain a usable model.

============================================================
22. MOST IMPORTANT OUTPUT
============================================================

The most important result is NOT a prediction score.

It is a trustworthy answer to:

"At the exact moment a new Kestrel job is submitted, what job-specific
information can the V42 controller legitimately know?"

Freeze that information set.

Only then should Runtime ML be retrained.
